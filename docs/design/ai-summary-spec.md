## 1. 产品逻辑总览

### 1.1 分级结构

```
年总结 ← 聚合当年 12 个月总结
  └─ 月总结 ← 聚合当月 4-5 周总结
       └─ 周总结 ← 聚合当周 7 天日总结
            └─ 日总结 ← 读取当天日记生成
```

每一级总结生成时，不直接读原始日记全文，而是**引用下一级的总结内容**，有效控制 Token 长度。

### 1.2 触发方式

**全部手动触发**，不做自动加载。AI 总结 Tab 内操作：

| 层级 | 触发位置 | 触发条件 |
|:-----|:---------|:---------|
| 日总结 | Tab 内切换至"日"视图 + 选择日期 | 当天有 ≥1 篇日记 |
| 周总结 | 切换至"周"视图 | 该周有 ≥1 篇日总结 |
| 月总结 | 切换至"月"视图 | 该月有 ≥1 篇周总结 |
| 年总结 | 切换至"年"视图 | 该年有 ≥1 篇月总结 |

### 1.3 保存策略

- 每次生成的总结**自动保存到数据库**
- 下次查看同一时间段时直接读取已保存结果（不重复生成）
- 每条总结有独立的"重新生成"和"编辑"入口

## 2. 后端设计

### 2.1 DB 模型

在 Prisma schema 新增 `Summary` 表：

```
model Summary {
  id          Int      @id @default(autoincrement())
  tier        String   // 'daily' | 'weekly' | 'monthly' | 'yearly'
  periodKey   String   // 日: '2026-07-29', 周: '2026-W30', 月: '2026-07', 年: '2026'
  content     String   // JSON: { analysis: { body, mental, psychological, growth }, advice: string }
  suggestions String?  // AI 建议
  raw         String   // LLM 原始返回全文（Markdown）
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
}
```

### 2.2 API 路由

| 方法 | 路由 | 说明 |
|:-----|:-----|:------|
| query | `summary.get` | 按 tier + periodKey 读取已保存总结 |
| mutation | `summary.generate` | 手动触发总结生成，返回并保存结果 |
| mutation | `summary.update` | 手动编辑总结内容 |
| mutation | `summary.regenerate` | 带用户反馈重新调用 AI 生成 |

### 2.3 generate 路由逻辑

```
generate(tier, periodKey, feedback?)
  → 判断 tier
    daily:   读当天日记（content 字段）
    weekly:  读当周 7 天日总结
    monthly: 读当月所有周总结
    yearly:  读当年所有月总结
  → 构造 system prompt + 源内容
  → 调用 llm.chat（复用已配平台）
  → 解析返回 JSON
  → 存入 Summary 表
  → 返回结果给前端
```

### 2.4 System Prompt 设计

```
你是一个专业的个人日志分析师。用户给你提供了以下日记/总结内容，请分析并返回 JSON：

{
  "analysis": {
    "body": "身体状态分析",
    "mental": "精神状态分析",
    "psychological": "心理状态分析",
    "growth": "成长与收获"
  },
  "advice": "给用户的建议（2-3条具体建议）",
  "summary": "一句话总结（非日总结层级用）"
}

注意：
- 每项分析控制在 50-100 字内
- 建议要具体可执行
- 保持客观和建设性
- 如果用户提供了反馈，优先修正之前的问题
```

### 3.2 层级切换器

位于 AI 总结 Tab 顶部：

```
┌─────────────────────────────────────────┐
│  [日] [周] [月] [年]  ◀ 2026-07 ▶     │ ← 日期导航
│                                         │
│  [7/27 一] [7/28 二] [7/29 三]         │ ← 具体日期选择（日视图）
│                                         │
│  [📋 生成今日总结]                      │ ← 生成/刷新按钮
└─────────────────────────────────────────┘
```

### 3.3 状态定义

| 状态 | 界面表现 |
|:-----|:---------|
| 未生成（有数据） | 显示"生成"按钮 |
| 已生成（有缓存） | 显示总结卡片 + 编辑/重新生成按钮 |
| 生成中 | 加载骨架屏 + "分析中..." |
| 无数据 | "该时间段暂无日记记录" |
| 生成失败 | 错误提示 + 重试按钮 |

### 3.4 编辑交互

**两种修改方式：**

1. **直接编辑** — 点击 ✏️ 编辑，总结卡片变为可编辑文本域，保存后调 `summary.update`
2. **AI 重新生成** — 点击 🔄 重新生成，弹出反馈输入框（可选），调 `summary.regenerate`

### 3.5 按钮布局

卡片右下角按钮组：

```
[✏️ 编辑] [🔄 重新生成]
         ↓ 点击重新生成
  弹出浮层："你觉得哪里不对？"
  ┌──────────────────────┐
  │ 对状态分析不够准确    │ ← 用户反馈输入
  │                      │
  │ [取消]  [✅ 重新生成] │
  └──────────────────────┘
```

## 5. 数据流

```
用户点击"生成周总结"
  → POST summary.generate({ tier: 'weekly', periodKey: '2026-W30' })
  → 后端读取该周 7 天日总结
  → 调用 LLM 生成（使用已保存的日总结）
  → 保存到 Summary 表
  → 返回结果给前端渲染
  → 后续用户查看该周，直接读缓存

用户点击"重新生成" + 输入反馈
  → POST summary.regenerate({ id: 42, feedback: "身体状态分析不够准确" })
  → 后端读取原总结 + 用户反馈
  → 调用 LLM 重新生成
  → 更新 Summary 表
  → 返回新结果
```
