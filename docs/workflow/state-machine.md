## 一、核心状态流转

```
                  ┌─────────────┐
     ┌──────────►│   TODO      │◄──────────┐
     │           └──────┬──────┘           │
     │                  │ 认领/PM 派发      │
     │           ┌──────▼──────┐           │
     │           │ IN_PROGRESS │           │
     │           └──────┬──────┘           │

     │           ┌──────▼──────┐           │
     │           │  SELF_CHECK │           │
     │           └──────┬──────┘           │
     │         ┌────────┼────────┐         │
     │   自评不合格  自评通过     │         │
     │         │        │        │         │
     │   ┌─────▼──┐  ┌─▼──────┐ │         │
     │   │ FIXING │  │   QA   │ │         │
     │   └────┬───┘  │ REVIEW │ │         │
     │        │      └──┬─────┘ │         │
     │        └─────────┼───────┘         │
     │             QA不通过│ QA通过         │
     │                  │                 │
     │           ┌──────▼──────┐         │
     │           │  DEPLOYED   │         │
     │           └──────┬──────┘         │
     │                  │ PM 确认验收      │
     │           ┌──────▼──────┐         │
     │           │  VERIFIED   │         │
     │           └──────┬──────┘         │

     │             │    │    │            │

     │           │     │                  │
     │           └──┬──┘                  │

    ┌──────────────┐

           │ 超过24h → 回归测试后恢复

    │  ROLLBACK    │ ← P0崩溃/数据丢失/futao指令
    └──────┬───────┘
           │ 回滚完成 → TODO（带回滚记录）
```

## 二、每个状态的 Gate Check

### TODO → IN_PROGRESS
- [ ] 需求已确认（有需求文档或 futao 口头确认记录）
- [ ] 不影响其他人在做的任务（PM 确认）
- [ ] 已知依赖项已就绪
- [ ] 负责人已明确

### IN_PROGRESS → SELF_CHECK
开发者自认完成时的前置条件：
- [ ] 功能代码写完
- [ ] 三轮自检完成：① 页面能加载 ② 核心功能正常 ③ 相关功能正常
- [ ] 错误态已覆盖（功能不可用时用户看到什么）
- [ ] 改动范围已记录（改了什么 + 受影响范围 + 已测试项）
- [ ] 测试数据已清理

### SELF_CHECK → QA_REVIEW
开发者自评完成后：
- [ ] 开发者自我评分（不合格/合格/优秀）——自评不合格不准提交
- [ ] 验收链接唯一（PM 确认）
- [ ] 提交说明包含：改了什么 + 受影响范围 + 已测试项
- [ ] PM 确认链接后通知 QA

### QA_REVIEW → DEPLOYED
- [ ] 冒烟测试通过（写/读/API/第三方集成）
- [ ] 异常路径覆盖测试通过（LLM 不可用/数据为空/网络超时等）
- [ ] QA 签字（不合格不留级）
- [ ] 验收标准 25 项逐项通过

### DEPLOYED → VERIFIED
- [ ] PM 确认未引入新问题
- [ ] 验收链接稳定可用
- [ ] 旧链接已废弃
- [ ] 通知 futao 验收

### VERIFIED → DONE
- [ ] futao 三档评分：
  - 优秀 → DONE，标注亮点
  - 合格 → DONE，标注可优化项
  - 不合格 → 附验收意见，自动打回 IN_PROGRESS
- [ ] 不合格时：agent 先复盘根因再修改，改完重走 SELF_CHECK → QA_REVIEW → DEPLOYED

## 三、问题纠错流程（Problem Fix Flow）

```
发现问题（验收中/futao 反馈）
    │
    ▼
1. 问题分级
   P0：核心功能不可用 → 立即停下手头工作修
   P1：功能异常但可规避 → 当天内修
   P2：体验优化 → 排期修
    │
    ▼
2. 根因分析（写下来，不写不准动手）
   需求没定义？ / 开发漏测了？ / 测试没覆盖？ / 交互设计没考虑到？
   写完原因再动手
    │
    ▼
3. 修补 + QA 复测
   必须回到 QA_REVIEW，不能修完直接丢给 futao
    │
    ▼
4. 复盘补丁
   这次缺少的检查项 → 加入 checklist
   流程中哪个 gate 没拦住 → 补强
```

## 四、暴力回滚（Force Rollback）

**触发条件**（仅限以下三种）：
1. P0 级功能崩溃（写日记/读取失败/数据丢失）
2. futao 明确要求回滚
3. 部署后造成数据损坏

**流程**：
1. 冻结当前分支（禁止任何人再提交）
2. 切回上一版本 + QA 冒烟（写日记能保存才算通）
3. 任务状态 → ROLLBACK（附回滚原因 + 时间戳）
4. 任务回 TODO 队列
5. 复盘：哪个 gate 没拦住？

**关键规则**：
- 回滚是 PM 权限，开发不能自行决定回滚
- 回滚后原任务不删除，状态标记为 `ROLLBACK`
- 重做时任务编号不变，版本号 +1

## 五、项目中断（Interruption）

**触发**：futao 要求暂停 / 更高优先级任务打断

**流程**：
1. 中断登记：
   - 当前任务的最后一个已知状态
   - 未提交的改动备份（git stash）
   - PM 记录中断原因 + 预计恢复时间
2. 任务状态 → PAUSED
3. 恢复时：
   - 从 PAUSED 状态继续
   - 恢复后先做 context check（中间其他人改了什么？）
   - 超过 24h → 回归测试 + QA 重测

## 六、各角色的职责

| 角色 | 状态机中的职责 |
|:----|:--------------|
| **开发者** | IN_PROGRESS → 自检完成 → SELF_CHECK；自评三档；不合格不提交 |
| **QA** | QA_REVIEW → 按验收标准逐项测试 → 三档评分 |
| **PM** | 状态机 gate keeper，控制每个状态的准入/准出；维护唯一验收链接 |
| **futao** | VERIFIED → 三档验收评分；不合格打回 |
| **小恒** | 确保需求不跑偏，记录每次需求变更 |
