## 1. 问题定位（分层诊断）

根据 @小恒 建议的分层方法 + @lamda 已实证的根因，问题定位如下：

| 层 | 状态 | 说明 |
|:--:|:----:|:----|
| ① 本地服务 | ✅ 稳定 | localhost:1111 一直 200，未崩溃 |
| ② tunnel 暴露层 | ❌ **真因** | cloudflared trycloudflare 免费隧道经常 530 掉线、URL 重启变化、IPv6/TLS 握手不稳 |
| ③ 机器资源 | ✅ 无瓶颈 | 未观测到 CPU/内存瓶颈 |

### ②层根因（已实证）
- **现象**：trycloudflare 免费隧道约 60 秒后静默掉线（530 / Failed to refresh DNS / control stream failure）
- **根因**：当前网络会静默终止**空闲的长连接**（约 60s 无流量即掐断），cloudflared 的 HTTP/2 长连正好是"空闲长连"
- **已验证缓解**：加 `--heartbeat-interval 1s` 保持心跳流量，实测稳定 80s+ 不掉
- **未解决问题**：URL 每次重启都变、免费层无 SLA

## 2. 候选方案对比

### 方案 A：cloudflared 免费隧道 + 心跳参数（现状修复）
| 维度 | 评估 |
|:----|:----|
| **稳定性** | ⭐⭐ 心跳参数缓解 60s 掉线，但免费层仍可能被掐 |
| **成本** | ¥0 免费 |
| **复杂度** | 低，一条命令加参数 |
| **URL 稳定性** | ❌ 每次重启变化 |
| **适用场景** | 临时验收、短期应急 |

**优点**：零成本，立即能用，@lamda 已实证参数有效
**缺点**：治标不治本，URL 变、免费层无 SLA、IPv6/TLS 握手不稳仍存在

### 方案 B：cloudflared Named Tunnel（固定域名）⭐ 推荐
| 维度 | 评估 |
|:----|:----|
| **稳定性** | ⭐⭐⭐⭐ 企业级边缘网络，远优于临时隧道 |
| **成本** | 免费（Tunnel 服务本身）+ 域名费（约 ¥50-80/年，.com 或免费 .tk） |
| **复杂度** | 中。需 Cloudflare 账号 + 一个域名，配置 DNS + 创建 Tunnel |
| **URL 稳定性** | ✅ 固定域名，永久不变 |
| **适用场景** | 中期方案，个人产品的标准做法 |

**优点**：
- 固定域名（如 logs.example.com），URL 永不变化
- 走 Cloudflare 全球边缘网络，稳定性远优于临时隧道
- 自带 CDN + HTTPS，零额外成本
- 免费层完全够用（个人使用流量极小）

**缺点**：
- 需要一个域名（每年几十块钱）
- 需要 Cloudflare 账号和域名 DNS 托管到 Cloudflare
- 首次配置约 15-30 分钟
- ⚠️ **Cloudflare 免费层代理请求有 100s 超时限制** → AI 总结等长请求需用**流式输出（SSE）**或改异步任务（对应此前 serveo 502 隐患，Phase 2 需提前规划）
- ⚠️ 国内访问走 Cloudflare 全球边缘，速度受运营商影响

**DNS 模式权衡**（@lamda 补充）：
- **橙云（Proxied，默认）** — 有 CDN 缓存 + 隐藏 IP，但长请求受 100s 代理超时限制，需 SSE/异步
- **灰云（DNS-only）** — 绕开代理无 100s 限制，请求直连 origin，适合 AI 总结这类同步长请求；代价是丢 CDN 缓存和隐藏 IP
- **部署建议**：先全灰云求稳，需要 CDN 时再局部切橙云

**配置要点**（@lamda 可执行）：
1. 注册 Cloudflare 账号，添加域名（DNS 托管）
2. `cloudflared tunnel login` 登录授权
3. `cloudflared tunnel create <name>` 创建隧道
4. 配置 DNS CNAME 指向隧道
5. `cloudflared tunnel run <name>` 运行（可设 systemd 服务自动重启）
6. 依然建议保留 `--heartbeat-interval 1s` 参数

### 方案 C：frp 自建内网穿透
| 维度 | 评估 |
|:----|:----|
| **稳定性** | ⭐⭐⭐ 取决于自建公网服务器的稳定性 |
| **成本** | 免费（frp 开源）+ 需一台有公网 IP 的服务器（约 ¥60-100/年学生机/轻量机） |
| **复杂度** | 高。需公网服务器 + 配置 frps/frpc + 防火墙规则 |
| **URL 稳定性** | ✅ 固定域名（自己的服务器 IP） |
| **适用场景** | 已有云服务器、需要完全自主控制 |

**优点**：
- 完全自主可控，不依赖第三方隧道服务
- 固定 IP/域名
- 可扩展支持 TCP/UDP 全协议（未来桌宠等功能可能需要）

**缺点**：
- 需要额外一台公网服务器（成本、运维）
- 配置复杂（frps + frpc + 防火墙 + 域名解析）
- 自己承担服务器运维（安全、更新、故障）

### 方案 D：商业内网穿透服务（cpolar / natapp / 花生壳）
| 维度 | 评估 |
|:----|:----|
| **稳定性** | ⭐⭐⭐ 商业 SLA，但免费版受限 |
| **成本** | 免费版可用但带宽/隧道数受限；付费版约 ¥10-40/月 |
| **复杂度** | 低，下载客户端即用 |
| **URL 稳定性** | 免费版 URL 随机，付费版可固定 |
| **适用场景** | 不想折腾、接受月付 |

**优点**：开箱即用，中文界面，客服支持
**缺点**：长期付费；免费版限制多（带宽、隧道数、URL 随机）

### 方案 E：云服务器托管（轻量应用服务器）
| 维度 | 评估 |
|:----|:----|
| **稳定性** | ⭐⭐⭐⭐⭐ 云厂商 SLA，最稳定 |
| **成本** | 学生机/轻量机约 ¥60-100/年（新用户优惠），之后续费约 ¥50-100/月 |
| **复杂度** | 中。需部署 Blinko 服务到云端，迁移数据 |
| **URL 稳定性** | ✅ 固定公网 IP + 域名 |
| **适用场景** | 长期正式部署、多端访问 |

**优点**：
- 最稳定，云厂商 SLA 保障
- 公网 IP 直接访问，无需穿透
- 弹性扩展（未来 AI 功能、桌宠需要更多资源）
- 国内云（腾讯/阿里）访问快

**缺点**：
- 需要迁移现有本地部署到云端
- 有一定月度成本
- 需要配置服务器安全（防火墙、HTTPS、备份）
- ⚠️ **国内节点需备案（1-2 周）** → 需提前规划，不能等需要时才启动
